# DF-007: organization authorization contract

Status: design only, 2026-10-17. No role enforcement is shipped in this documentation task. Authentication and session lifecycle are specified in [AUTHENTICATION.md](AUTHENTICATION.md).

## Access model

A User is a global identity. Membership connects one User to one Organization, with status ACTIVE/SUSPENDED/REMOVED. An Organization is ACTIVE/ARCHIVED. Unverified/disabled users, inactive memberships and archived organizations cannot use normal workspace routes. Reopening/exporting an archived workspace needs an explicit owner-only lifecycle flow, not a general bypass.

Use scoped role grants: OWNER, ADMIN and HR at organization scope; PROJECT_MANAGER with organization-scoped project creation and a separate manager assignment for each project; TEAM_LEAD only for assigned teams; EMPLOYEE at organization scope plus explicit project membership; VIEWER only for explicitly shared project reports. A user can have multiple scoped grants. An owner/admin has organization-management authority but does not automatically become HR or gain private wellbeing data. OWNER is exclusive to exactly one active membership per organization initially; transfer is an atomic, audited, recently reauthenticated operation to another verified active member. Do not delete/suspend the last owner or let concurrent transfers produce zero/multiple owners.

All mutations first resolve the actor's current active membership, then apply action permission, resource relationship and field restrictions. Deny by default. Capability union applies only inside the same organization; explicit private-data restrictions and separation of duties override the union. In UI explanations distinguish organization roles from project/team assignments. Never use string role ordering such as ADMIN > HR > EMPLOYEE to infer access.

The organization-scoped PROJECT_MANAGER grant permits creating a project and atomically assigning the creator as its manager. It grants no access to other projects; only owner/admin can assign or replace another project manager. Subsequent project management requires its explicit manager assignment.

Team leads can assign only active members of their assigned team who also belong to the target project; team leadership is not project membership. A project manager cannot grant organization roles or add outsiders; project membership changes select existing active organization members. Owner/admin authority to manage project work does not include HR-sensitive records. Owner may explicitly appoint a separate HR grant with audit; that role change itself must never silently expose private reflections. For privacy, HR approval is the initial attendance-correction approver; configurable delegated manager approval is a future explicit policy, not an implicit Team Lead permission.

A viewer receives only the report's explicit field projection. Raw tasks, member directory, individual time logs, leave details and linked GitHub repository content stay denied unless independently authorized. An owner-wide report aggregates authorized operational data and excludes private HR/wellbeing fields. Sharing is authenticated and organization-bound initially; no public report links.

## Sensitive fields and separation of duties

- Directory exposes only work identity, title, team and optional work timezone/availability, not private contact details or exact location. Public availability shows busy/free/out-of-office, never leave reasons or private calendar entries.
- HR sees only necessary employee administration/attendance/leave fields. Private reflections remain author-only; explicit sharing would require a separate feature and recipient grant. AI tools inherit these same field scopes and cannot receive private content merely because a manager asks.
- Employees submit corrections instead of rewriting approved time records. An approver cannot approve their own leave/correction even if they also hold OWNER/ADMIN/HR. Another HR-granted active member must approve; without one the request remains pending.
- Granting HR/Project Manager/Employee/Viewer is limited to owner/admin. Admin cannot modify owner/admin memberships, elevate themselves to owner/admin, or remove the owner's access. Only the owner manages Admin grants. Ownership cannot be assigned through an invitation. Administrative grants/removals require recent reauthentication and audit. Future integrations never return stored provider secrets through read endpoints.
- A membership suspension/removal immediately invalidates its project/team grants. Restoring membership does not silently resurrect grants: reissue them explicitly. Organization archiving blocks all ordinary members including the owner, apart from the narrowly defined lifecycle route.

## Persistence invariants for DF-008 and later

Use UUID primary keys, unique User.normalizedEmail, unique Membership(organizationId,userId), and a unique composite Membership(organizationId,id). Child tables carry organizationId. Composite foreign keys such as `(organizationId,membershipId)` prevent attaching a member from organization B to organization A. Project/team assignment tables similarly reference `(organizationId,projectId/teamId)` and `(organizationId,membershipId)`; assignment uniqueness includes the scope. Role values are enums, and scope/grant combinations are checked in service validation plus SQL CHECK constraints where representable.

Organization.ownerMembershipId is a non-null, unique-per-organization pointer to an in-organization active membership, rather than an independently editable OWNER role row. Bootstrap uses application-generated UUIDs and a deferred SQL foreign-key constraint in a reviewed migration to insert the organization/membership atomically; if Prisma cannot represent a constraint, retain it in migration SQL and test it against PostgreSQL. OWNER capability derives from this pointer; ordinary grants cannot create another owner. Owner activity, transfer and suspension invariants require a transaction locking the organization row.

Queries receive an AuthorizedOrganizationContext created by the guard after validating the live session and active membership. Client-supplied organizationId/resource IDs are selectors only. Read/update/delete queries include organizationId and relationship predicates; unauthorized nested resources yield generic 404. DTOs allowlist writable fields, never spread request objects into Prisma writes. IDs being unguessable is not authorization. List/count/search/pagination/export/download routes must apply the same filters before aggregation or pagination.

For sensitive writes, re-check membership/grants and resource state inside the transaction and lock the relevant membership/organization/grant rows. Revocation and writes must share the locking protocol: a write committed before revocation is auditable; once revocation commits no later write may use a stale authorization result. Do not cache positive permissions across requests initially. Scope audit events, queues, SSE/WebSocket subscriptions, file URLs, caches and AI retrieval by organization and recipient; disconnect/recheck access after grant changes. RLS is possible future defense in depth, not currently deployed or a substitute for these predicates.

## Required negative tests

| Scenario                                                                                  | Expected outcome                                                           |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Organization A member guesses B's resource UUID, including nested/list/count/export paths | Generic 404 / no rows or counts from B                                     |
| A project manager changes body role/organizationId or adds an outsider                    | Validation/permission denial; no write                                     |
| Team lead addresses another team's task or non-member project                             | Denied                                                                     |
| Admin attempts to promote self, change owner or grant Admin                               | Denied and audited                                                         |
| Two requests remove/transfer owner concurrently                                           | Exactly one valid owner remains                                            |
| Membership/grant revoked while a mutation is in flight                                    | Transaction locking defines the order; no post-revocation authorized write |
| Employee/HR approves own leave or correction                                              | Denied regardless of role union                                            |
| HR/admin requests another person's reflection or viewer requests raw worklogs             | Denied; no sensitive fields in errors/exports                              |
| Suspended membership restored without grants                                              | Old project/team access stays denied                                       |
| Forged header, role field, selected-workspace cookie, cached role or stale session        | No authority gained                                                        |
| Cross-organization composite foreign key attempted directly in integration test           | PostgreSQL rejects it                                                      |
| User switches organization or logs out with cached private content                        | Cache cleared; next access reauthorized                                    |

Pair each deny case with the corresponding authorized case. Parameterize tests across all seven role categories and include multi-role/multi-organization users. DF-008 initially covers identity/organization/membership isolation; resource-specific tests land with their feature. This matrix does not claim those future modules exist.
